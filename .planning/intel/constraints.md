## Mod Profile Format (`mod-profile`, schemaVersion 1.1)
- source: docs/profile-spec.md
- type: schema
- content: Portable JSON format for sharing mod loadouts. Format ID `mod-profile`, current schema version `1.1`, file extension `.modprofile.json`, share code prefix `mp1:`, proposed MIME `application/vnd.modprofile+json`. Required top-level fields: `format` (literal `"mod-profile"`), `schemaVersion` (MAJOR.MINOR; readers MUST refuse an unknown MAJOR), `game`, `exportedAt` (ISO 8601 UTC), `exportedBy` `{tool, version}`, `profile` `{name, description?, author?}`, `mods` (ordered array); `extensions` optional. Deadlock identity: `steamAppId` 1422450, `gameBananaGameId` 20948; readers MUST refuse a profile whose game does not match their target game. Each `mods[]` entry has `source` (open enum, currently `"gamebanana"`), `ref`, `enabled`, `priority` (integer, lower loads first; Deadlock VPKs accept 1-99), and optional `hint`. GameBanana `ref` is `{submissionId, fileId}` plus optional `section` and `vpkStem` (added in 1.1; the variant key when one file expands into multiple VPKs, lowercased, omitted when uninformative). Non-goals: hosting profiles, social features, transporting mod files; the format is references-only.

## Mod Profile resolution, share code, and versioning rules
- source: docs/profile-spec.md
- type: protocol
- content: Resolution per mod entry: resolve `ref` against `source`; if the exact `fileId` is gone or flagged archived, resolve to the newest non-archived file of the same `submissionId` and surface it as "upgraded"; if the submission is 404, mark unresolvable and show the `hint`; the importer SHOULD present a per-row preview (exact / upgraded / unresolvable) and allow per-row opt-out before downloading. Share code is `mp1:<base64url(gzip(json))>` (RFC 4648 section 5, no padding); the decoder MUST validate the prefix, decode, decompress, validate against the spec, and MUST cap the inflated payload to bound gzip-bomb risk (Grimoire's limit is 256 KB inflated). Extensions are namespaced by tool; readers MUST ignore unknown extension keys, MUST NOT alter or strip them when re-saving, and extensions MUST NOT carry data required for correct mod resolution. Additive changes bump MINOR, breaking changes bump MAJOR; readers MUST refuse an unknown MAJOR and SHOULD accept higher MINOR by ignoring unrecognized fields.

## Mod Profile security requirements for implementers
- source: docs/profile-spec.md
- type: nfr
- content: A foreign profile is untrusted input. Validate the entire structure against the schema before acting on any field. Treat all strings in `profile.*` and `hint.*` as plain text and never render as HTML. Show the user a preview of every mod, every autoexec command, and every extension payload before applying anything. Never auto-execute `autoexecCommands` without the user explicitly opting in. Honor the user's NSFW filter when previewing thumbnails. The format bundles no binary content, so importers MUST validate downloaded files (size, hash if known, archive contents).

## vpk-modinfo v1: embedded VPK identity metadata
- source: docs/vpk-modinfo-spec.md
- type: schema
- content: Status v1, stable (schemaVersion 1); this document is the source of truth for the format and is tool-neutral. Every imprinted VPK carries BOTH root-level entries, written together in a single repack: `addoninfo.txt` (KeyValues1 human summary and minimal machine-readable identity anchor) and `modinfo.json` (the complete machine record). `addoninfo.txt` keys appear in exactly this order: `addonversion`, `addontitle`, `addonauthor`, `gamebananaId`, `gamebananaFileId`, `sourceUrl`, `buildDate`, `originalSha256`, `originalSize`, `originalCrc32`, `modinfoVersion` (always last). KV1 values are single-line only (normative): writers MUST strip or reject control characters below 0x20 and 0x7F. `modinfo.json` is discriminated on `kind`: `"mod"` or `"merge"`; merge records carry a full `sources` array (one entry per source mod in merge input order, each with `title`, `identity`, `priorityAtMergeTime`, `enabledAtMergeTime`, `fileNameAtMergeTime`) and set `author` to exactly `"Multiple (merged)"`.

## vpk-modinfo canonical identity model
- source: docs/vpk-modinfo-spec.md
- type: protocol
- content: The load-bearing rule of the format. The canonical identity of a VPK is its ORIGINAL, pre-first-imprint whole-file sha256; it is fixed at the moment of first imprint and never changes, no matter how many times metadata is rewritten. Rules: (1) first imprint computes sha256 (and optionally size, crc32) from the file's bytes BEFORE the repack and sets `firstImprintedAt`; (2) re-imprint carries forward exactly two things verbatim, the `identity` triple and `firstImprintedAt`, and never recomputes "original" from already-imprinted bytes; (3) a merged VPK's original is its pre-embed merge output (merge, hash, then embed in a second pass); (4) reader resolution order is embedded original identity when well-formed, else the live whole-file hash; (5) never re-stamp stored hashes held outside the file. Within a major version evolution is additive-only; readers MUST tolerate unknown keys, and an unrecognized `schemaVersion` means the `modinfo.json` record is treated as absent while the frozen `addoninfo.txt` identity keys still stand.

## vpk-modinfo writer and reader requirements
- source: docs/vpk-modinfo-spec.md
- type: protocol
- content: Writers: both entries in one repack, never one without the other; injected entries win on collision; respect foreign embeds (refuse to imprint over an `addoninfo.txt` with no recoverable vpk-modinfo identity rather than clobber it); accept that a repack is not byte-stable (entry order is nondeterministic, VPK-level checksums are zeroed or dropped, output is a single self-contained `_dir.vpk`, and a multi-chunk VPK must be refused unless the whole set is repacked); never write output over input (repack to a temp path, verify, atomically rename); verify entry-tree parity before the swap; refuse drifted files. Readers: missing or malformed means absent and reading metadata must never fail the surrounding operation; never trust partial records; match entry names at the VPK root case-insensitively after normalizing backslashes; validate `sha256` against `^[0-9a-f]{64}$`; preserve merge records (a single-mod-only tool must not rewrite a `kind: "merge"` record as `kind: "mod"`); treat embedded data as self-reported. Matchers must consult the embed first, exclude `addoninfo.txt`/`modinfo.json` (and the legacy `grimoire_meta.json`) from entry-set content signatures, and use the embedded original identity when matching against external indexes.

## VPK imprinting: Grimoire integration
- source: docs/vpk-metadata-embed-integration.md
- type: protocol
- content: Canonical identity of a VPK is its original pre-first-imprint whole-file sha256 and never changes when the file is imprinted. Everything stored is on the original axis (`metadata.sha256`, `MergedModSource.sha256AtMergeTime`, locker `sha256AtApplyTime`); an imprinted mod's `metadata.sha256` stays the original and is NOT re-stamped. `resolveVpkIdentity(path)` (`vpkIdentity.ts`) is the single resolver. Division of labor: Grimoire owns all serialization, hashing, and idempotency (`modinfoFormat.ts`); vpkmerge is a dumb byte-embedder that embeds opaque blobs via the repeatable `--extra-file ENTRY=PATH` flag and never interprets them. Unknown-mod identification consult order: (1) embedded metadata (always on, ungated, offline), (2) local CRC cache, (3) network GameBanana CRC matcher (last resort, stays behind `experimentalUnknownModMatching`). In-place imprint mechanics: repack to a temp dotfile in the mod's own folder, parity-check against the input's entry tree, atomic rename; runs under `runExclusiveModMutation`; refuses to imprint a mod the running game has loaded; anomaly guard refuses `empty`, `unparseable`, `chunked`, `foreign-embed`, and `hash-drift`. Install-time imprinting is gated behind `experimentalVpkImprinting` (default off); merge-path embedding is always on, so a merged VPK is born imprinted. Phase 4 (ship: vpkmerge release + `VPKMERGE_VERSION` and sha256 bump) is deferred; dev uses the auto-discovered sibling `../vpkmerge/target` build.

## Deadworks server browser: data flow and content provisioning
- source: docs/deadworks-servers.md
- type: api-contract
- content: Gated behind the `experimentalDeadworksServers` setting. List: `GET <relay>/v1/servers` (falls back to `/api/servers` for a deadworks-shaped relay); each row is A2S-pinged over UDP. Join (`prepareAndConnect`): `GET <relay>/v1/servers/:id/content` returns a manifest of `.vpk.bz2` items (`kind: map | addon`, `version`, `download_url`); ensure `gameinfo.gi` mounts the deadworks content path; for each item not already at the manifest version, download, decompress via bundled 7-Zip, verify the VPK magic (`0x55aa1234`), then atomically rename onto the canonical path, with a `deadworks_cache/versions.json` ledger skipping already-current files; open `steam://connect/<ip:port>` via `shell.openExternal`. Maps land in `citadel/maps`, addons in `citadel/deadworks_addons/vpks`. The relay URL is configurable (`deadworksRelayUrl`), defaulting to `https://relay.grimoiremods.com`; wire types mirror `grimoire-relay/src/shared/schemas.ts` and the client copy `src/types/deadworks.ts` must stay additive and in sync. Joining is fully cross-platform; hosting a Deadworks game server still requires Windows and is out of scope.

## Deadworks gameinfo.gi SearchPaths integration
- source: docs/deadworks-servers.md
- type: protocol
- content: The load-bearing part. Grimoire owns and rewrites the entire `SearchPaths` block of `gameinfo.gi` (`system.ts`, canonical `SEARCH_PATHS_BLOCK`), so a Deadworks-style `addonroot` line added out-of-band would be erased the next time the user runs Fix Configuration. The Deadworks content path is therefore a first-class conditional line inside grimoire's own canonical block: `deadlock.ts` exposes `DEADWORKS_SEARCH_PATH = 'citadel/deadworks_addons/vpks'` and `hasDeadworksContentRoot()`; `buildSearchPathsBlock(overflow, includeDeadworks)` appends it as the LAST entry of the addon group (lowest precedence, so user mods always win a file collision); `getGameinfoStatus` / `fixGameinfo` treat the deadworks line as required whenever content has been provisioned; `ensureDeadworksSearchPath()` is the connect-time guard and runs before downloading so a locked or unparseable `gameinfo.gi` fails fast.

## Deadworks security constraints
- source: docs/deadworks-servers.md
- type: nfr
- content: Manifest filenames are validated as a single safe path component (mirroring the relay's Zod guard) before any filesystem write. A 4 GiB decompression ceiling bounds a bz2-bomb manifest. No telemetry: unlike the upstream Deadworks launcher, Grimoire sends no install or heartbeat pings.

## Locker Hero Card APPLY pipeline
- source: docs/locker-hero-card-apply.md
- type: protocol
- content: Status shipped (re-verified 2026-07-28); this is the design of record and the "As built" section records where the implementation deviates. Decided model: every applied card lives in a SINGLE Locker-managed cosmetics VPK, rebuilt from a selection set whenever a card is applied, swapped, or reverted. Rationale: decoupled lifecycle (changing or disabling a skin never touches cards), one slot for all cards (per-hero card paths are disjoint), and composition by slot rather than by merge. `rebuildLockerCosmetics(deadlockPath, selections)` is the one operation; apply, swap, and revert are all "edit the selection set, then rebuild": empty set deletes the VPK and its metadata; each selection's source VPK is located by fileName with a `sha256AtApplyTime` fallback and a missing source is dropped with a reported warning; each source is split on prefix `panorama/images/heroes/<codename>_` (the trailing underscore prevents leaking into a hero whose codename shares a stem); 1 source is used directly, 2+ are combined with `vpkmerge merge --strict`; the output is verified and swapped atomically. The cosmetics VPK is hidden from Installed, Locker, Conflicts, profile save/switch, and portable-profile export via the centralized `isLockerManaged` signal. Deviations as built: (1) the VPK is written inside the grimoire SearchPaths directory (`lockerCardsVpkPath`) and wins by SearchPaths precedence, so no load-order pinning is involved and the selection set lives under the synthetic `LOCKER_CARDS_KEY`, superseding the pakNN/`pinLockerVpksToFront` model described in section 6; (2) source identity is a folder-relative `metaKey`, not a bare filename; (3) custom uploads resolve to a per-codename staging VPK built by `vpkmerge icon`; (4) variant scope captures the whole per-hero panorama prefix set and apply copies bytes without depending on the preview decode; (5) the missing-source warning is surfaced through `reportMissingSources`.

## Live 3D hero poses in the Locker
- source: docs/hero-pose-locker.md
- type: protocol
- content: The per-hero Locker view shows a 2D portrait by default with a 2D/3D toggle (lg+ only); 3D renders a live orbitable still of the hero in their menu pose, reflecting the currently-enabled skin. `vpkmerge model export --pose [CLIP[@FRAME]]` bakes one animation frame into the mesh and emits a static `.glb` with no skeleton, skin, or clips, so there is no `SkinnedMesh` and no skin-strip hack. Deadlock's NPR shells are dropped on export (`*_outline` inverted hull, additive `*_glow`, comic-style inked `*jitter*`), detected by material/mesh-part name and never by texture-param name. For a skin, the menu-pose clip is mapped from `--base` onto the skin rig by bone name. `--require-pose` makes a clipless WIP hero error out so the Locker falls back to the 2D portrait rather than showing an unposed model. Requires vpkmerge v0.6.0 for `--pose` (v0.6.1 for deterministic hero-model discovery, `--require-pose`, and the `*jitter*` shell drop); the bundled binary is pinned in `scripts/fetch-vpkmerge.mjs` via `VPKMERGE_VERSION` plus three sha256s. Storage: `userData/hero-poses/<sanitized-key>/model.glb`, served through the privileged `grimoire-hero://m/<encoded-key>/model.glb?v=<mtime>` scheme because the renderer cannot read userData under `file://` + webSecurity; each pose dir carries a `.cache-version` marker (`POSE_CACHE_VERSION`) and a mismatch regenerates in place.

## Localization (i18n) pipeline
- source: docs/localization.md
- type: protocol
- content: `i18next` + `react-i18next`, init in `src/i18n.ts`. Catalogs are `src/locales/<lang>/translation.json`, i18next JSON v4 format. Only English is bundled into the build; every other language is downloaded at runtime, cached under `userData/locales/<code>/`, and registered via `registerDownloadedCatalog`/`hydrateDownloadedLocales`. On startup a background `refresh` conditionally re-fetches each downloaded catalog using a stored ETag with `If-None-Match` and live-swaps any that changed on `main`, so fixing a translation needs no client release; only brand-new English source keys need one. `src/locales/manifest.json` (generated by `scripts/gen-locale-manifest.mjs`) is the language index with per-language completion percentages, regenerated with `pnpm i18n:manifest`; CI fails on a stale manifest. Detection uses `navigator.language` by default, overridable in Settings and persisted in `AppSettings.language`. Weblate component settings are fixed: file format i18next JSON v4, file mask `src/locales/*/translation.json`, monolingual base `src/locales/en/translation.json`, Edit base file off, language code style BCP 47 (hyphenated, so `pt-BR` not `pt_BR`, which is what i18next matches).

## Localization developer and translator rules
- source: docs/localization.md
- type: nfr
- content: Never hardcode user-facing English; use `t('namespace.key')`. Only ever edit `src/locales/en/translation.json`; every other language file is owned by Weblate and hand-editing causes merge conflicts. Namespace by surface and keep keys descriptive rather than the English text itself. Define `key_one`/`key_other` for plurals and call `t('key', {count})`. Use `{{name}}` interpolation and never build sentences by concatenating fragments; each sentence is one key. Before committing run `pnpm i18n:check` (fails if any referenced key is missing from the English catalog) and `pnpm i18n:manifest`; CI re-checks both. Translators must keep `{{placeholders}}` exactly as written, must not translate brand and proper names (Grimoire, Deadlock, GameBanana, Steam, Discord, gameinfo.gi, VPK), should punctuate naturally for their language (the no-em-dash rule is an English-source rule only), and should leave a string untranslated rather than guess.

## Multi-folder addon overflow
- source: docs/multi-folder-addon-overflow.md
- type: protocol
- content: Status implemented (W1-W10 landed; renderer polish W11 optional). Lifts the effective 99-mod ceiling by overflowing enabled mods into sibling `citadel/addons1..addons9` folders, each with its own `pak01`-`pak99` namespace and its own additional `Game` search path. The 99 is not an engine cap, only the per-folder two-digit `pakNN` naming convention. Core model: an ordered set of addon roots (index 0 = `addons`), with `.disabled/` remaining a single shared parking lot under base `addons`. Asymmetric keying is the backwards-compat guarantee: base `addons/` and `.disabled/` keep the bare filename as metadata key and id source, while overflow `addons{N}/` uses `addons{N}/<filename>`, so no existing mod is re-keyed and no migration runs. Load-order Model A (confirmed by in-game test, Gate 0 resolved 2026-05-27): folder order in SearchPaths is the primary precedence key, then ascending `pakNN` within the folder; global position = `folderIndex * 99 + slot`, with the reverse mapping `folderIndex = floor((pos-1)/99)`, `slot = ((pos-1) % 99) + 1`. `MAX_ADDON_FOLDERS = 10` (base + addons1..addons9 = 990 slots). Overflow paths are lazy-listed: the folder is created and its `Game` path added in the same operation, so a missing folder is never listed. `hasRequiredSearchPaths` keeps requiring only base `addons` + `grimoire`, so overflow paths stay additive and no existing user reads as misconfigured. Conflict grouping keys on `(folder, pakNN)`, cosmetics scanners and the vanilla stash cover every addon folder, and `allocateEnabledVpkPath` is the shared base-first allocator.

## APT repository (Debian / Ubuntu)
- source: docs/apt-repo.md
- type: protocol
- content: Grimoire ships an APT repository at `https://apt.grimoiremods.com` because the in-app updater (electron-updater) cannot self-update a `.deb` install; `getInstallSource()` in `updater.ts` detects `/opt` installs as `managed` and disables the in-app updater. Hosting is a Cloudflare R2 bucket (`grimoire-apt`) served by the `grimoire-apt` Worker, which streams objects from the bucket and tallies real `.deb` downloads in KV. The `apt-publish` job in `.github/workflows/release.yml` runs on each tagged release, rebuilding a fresh GPG-signed latest-only repo from that release's `.deb` with `reprepro` and syncing to R2 with `--delete`. Source of truth for old versions stays GitHub Releases; the apt repo only ever offers the newest version. Scope is `amd64` only (Arch users use the AUR `grimoire-bin`). The job is gated on the repo variable `APT_PUBLISH_ENABLED == 'true'`. The signing key is a dedicated passphraseless RSA-4096 key (RSA over ed25519 for widest apt compatibility). The `dists/` index is uploaded with `Cache-Control: no-cache` and `pool/` debs with a long immutable max-age, so the CDN cannot serve a stale package index after a release.

## Discord Rich Presence
- source: docs/discord-rpc-setup.md
- type: protocol
- content: Rich Presence talks only to the user's locally-running Discord client over an IPC socket (`$XDG_RUNTIME_DIR/discord-ipc-0` on Linux, `\\?\pipe\discord-ipc-0` on Windows). Grimoire itself opens no network connection and sends nothing to any Grimoire server, so the offline-first / no-phone-home promise holds. Because it broadcasts activity outward through Discord, it is off by default and lives behind `settings.discordRpcEnabled` (Settings -> Preferences). Code layout: `discordRpc.ts` owns the connection lifecycle, per-surface wording, art keys, buttons, the elapsed timer, and the rate-limit throttle (Discord allows 5 activity updates / 20s); `ipc/discord.ts` handles `discord:update` / `discord:clear`; `DiscordPresence.tsx` is a headless renderer component reporting `{surface, count}` on navigation, debounced. Library is `@xhayper/discord-rpc` (pure JS, no electron-rebuild). `DISCORD_CLIENT_ID` is a public non-secret Application ID; blanking it is the kill switch. One portal step remains: upload a square logo with asset key `grimoire_logo`. Per-hero Locker art uses the hero's public Deadlock wiki image as an external `large_url`, so no per-hero assets need uploading. Known limitation: Flatpak/Snap sandboxes can hide the Discord IPC socket, and the app degrades quietly.

## Grimoire Social: process boundaries and data model
- source: docs/social-architecture.md
- type: schema
- content: Process boundaries: the renderer (`Discover.tsx`) is presentation only and talks to `window.electronAPI.social.*`; the main process (`electron/main/services/social.ts`) owns the session token via `safeStorage`, wraps fetch calls, applies the same rate-limiter pattern as `gamebanana.ts`, and never exposes the token to the renderer; the Workers edge is stateless request handling; D1 is the source of truth. ## UI shell rule: which chrome belongs to what
- source: docs/design-overhaul-brief.md
- type: protocol
- content: Three kinds of surface, each owning a fixed amount of chrome. A **top-level route** is a sidebar destination and uses `PageHeader` with a title, description, and actions (Conflicts, Browse, Settings, Servers, Discover, the Foundry landings). A **drill-in** is reached from a grid or card and keeps a Back control; the shell owns identity, background art, the rail, and Back, and its sections are panels inside that shell that never render their own `PageHeader` or Back (Locker Global, Locker hero, Foundry hero workshop). A **section body** renders content and nothing else, named `*Shelf` or `*Panel`. Three navigation invariants follow: (1) a tab switch never changes the shell, checked mechanically by capturing a shell node, switching sections, and confirming the node is still in the document; (2) a route that presents itself as a section of X can return to X; (3) section state is addressable and survives a round trip. A `role="tab"` is a promise about all of the above: either wire it fully (`aria-controls` to a real `role="tabpanel"`, `aria-labelledby` back, roving `tabIndex`, arrow-key movement) or use plain buttons and drop the role. One panel, not one per tab: every tab's `aria-controls` names the same id and the panel's `aria-labelledby` follows the selected tab.
