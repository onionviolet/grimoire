<interfaces>
Contracts the executor needs. Do not go looking for these in the codebase.

The renderer bridge that reports what the loaded catalog contains, reachable from a driven
build through `window.electronAPI`:

```typescript
window.electronAPI.foundry.ensureThumbnails(category: TextureCategory): Promise<TextureGridItem[]>;
// TextureGridItem extends TextureEntry { path: string; category: TextureCategory; hero: string | null; label: string }
```
`hero` is the panorama codename the catalog itself carries, which is exactly the fact Leg B
needs on the catalog side.

The resolver side, after plan 05-02, is readable off the rendered DOM rather than through a
module import. `buildHeroFilterOptions` (`src/components/foundry/heroFilterOptions.ts`) puts a
codename that resolves to no hero into the listbox with the codename as its own label, the
`foundry.filters.unreleasedGroup` string ("Unreleased or internal") as its hint, `muted: true`,
and sorted below the real roster. A codename that resolves gets a hero name as its label and
the codename as its hint.

The driver, per CLAUDE.md's "Driving a Running Dev Build":

```bash
GRIMOIRE_DEV_SLOT=<N> pnpm dev
GRIMOIRE_DEV_SLOT=<N> node scripts/dev-driver.mjs eval "window.__GRIMOIRE_DEV_SLOT"
GRIMOIRE_DEV_SLOT=<N> node scripts/dev-driver.mjs route foundry
GRIMOIRE_DEV_SLOT=<N> node scripts/dev-driver.mjs text <selector>
GRIMOIRE_DEV_SLOT=<N> node scripts/dev-driver.mjs html <selector>
GRIMOIRE_DEV_SLOT=<N> node scripts/dev-driver.mjs evalfile <path>
```
Slot N derives the Vite port, the CDP port and an isolated user-data directory. Slot 2 is
Vite 5175 and CDP 9224. A slot copies the real profile on first boot, so it opens with actual
mods and settings. The app mounts a HashRouter, so `route` sets `location.hash`.

<planner_decisions>
Recorded so the executor does not re-litigate them.

- **Whether the Abrams defect is reachable through the dual alias-table structure: this plan measures it rather than assuming either way.** RESEARCH.md's most concrete lead is that Foundry's `?hero=` route matching at `Foundry.tsx:161-162` resolves through `HERO_DISPLAY_ALIASES` in `lockerUtils.ts` while the other three D-11 call sites resolve through `heroIdentity.ts`. Plan 05-02's Leg A now proves those two tables cannot disagree for any hero in the roster, which downgrades the lead considerably but does not close it, because Leg A cannot see what either table omits. Leg B is what sees omission. If Leg B finds no alias miss, the honest recorded conclusion is that the dual-table structure is ruled out as the cause of #4 and the empty state was honest, not that the sweep found nothing.
- **How Leg B reads the resolver side.** Not by importing the table into a script, which would only re-run Leg A in a different process, but off the rendered hero filter in the driven build, which is the resolver's real output at the point a user meets it. `docs/portrait-alias-sweep-plan.md` anticipated exactly this once `heroFilterOptions.ts` landed. Reading the DOM also catches a failure Leg A structurally cannot: a resolver that is correct but is not consulted at that call site.
- **The unblocking condition the doc named has been met.** The doc paused Legs B and C on 2026-07-30 for two reasons: uncommitted in-flight work on this exact surface, and a dev server already attached. `heroFilterOptions.ts` and `HeroSelect.tsx` have since landed, and the slot mechanism documented in CLAUDE.md removes the single-server contention by giving this run its own Vite port, CDP port and user-data directory. Both reasons are discharged, and the doc's Running-concurrently section should be updated to say so rather than left reading as a live blocker.
- **A blocked row is a real outcome, not a failure of the plan.** If no free slot can be obtained, every unresolved row is recorded as blocked with a per-row reason. That is the same distinction Phase 1 drew between blocked and deferred: blocked keeps the record saying someone still owes the reading. What is forbidden is a row that is absent, or one that claims a verdict from a source read rather than a driven build.
- **The sweep patches nothing.** If Leg B finds an alias miss, the finding is written down with the hero, the codename and the evidence, and closing it is a follow-up. Patching a table inside a measurement plan would make the measurement unreproducible against the build it measured.
</planner_decisions>
