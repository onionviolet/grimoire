which is exactly five characters, so the `name.length > 5` guard that strips a `pakNN` prefix
does not fire, and the title-casing step turns it into `Pak92`:

```typescript
function extractModName(filename: string): string {
    let name = filename.replace(/_dir\.vpk$/, '').replace(/\.vpk$/, '');
    if (name.startsWith('pak') && name.length > 5) {
        const rest = name.slice(5);
        name = rest.startsWith('_') ? rest.slice(1) : rest;
    }
    return name.replace(/[_-]/g, ' ').split(/\s+/).filter((w) => w.length > 0)
        .map((w) => w.charAt(0).toUpperCase() + w.slice(1)).join(' ');
}
```

<planner_decisions>
Recorded so the executor does not re-litigate them.

- **What counts as an unnamed pak.** A mod whose display name is exactly the word `Pak` followed by digits, case-insensitively. That is the precise output `extractModName` produces for a `pakNN_dir.vpk` with no other name, and it is narrow enough that a real mod called something like `Pak Rat` is untouched. Detection lives in the pure module so it is testable, not inline in the render.
- **Derivation reads the mod's own VPK, not its metadata.** This is the same move the Announcer-shelf fix already made for sound classification: the VPK directory is the mod's own statement of what it writes, and a name or a category is a label someone chose. Reusing `list-unknown-mod-files` means no new IPC channel and no new privilege.
- **The cap is three entries plus a count.** This settles the UI-SPEC's E8 `overflow` backstop, which left the exact cap undecided. Three is the size the source docs' own Announcer-shelf examples run to, and the remainder is stated as a count rather than truncated silently, so a pak that writes forty files still says forty rather than showing a clipped string.
- **Unreadable and empty produce the same label.** D-19 asks for unknown to be labelled unknown; splitting that into "could not read" and "read but empty" would give the user two messages they cannot act on differently. One honest admission.
- **The Global visual card is the only render site this plan changes.** The sound shelf's rows already derive their identity from exact entry paths and are out of scope; widening this to every surface that renders a mod name would be a different, larger change than the defect the requirement names.
- **How REQ-sound-locker-surface is answered.** It is not answered by building anything, and it is not silently dropped. D-01 makes the Locker Global drill-in the canonical home and refuses the dedicated route's return; D-02 keeps every useful capability of the folded-back variant inside that shell. Both are already true in the tree: `GlobalSoundShelf` is a body component mounted inside `LockerGlobalView`, and `legacySoundTarget` plus `resolveLockerRoute` rewrite the shipped `/locker/sounds*` URLs. Plan 05-01 adds test cases proving those rewrites survive the widened default. This plan writes that chain down in the traceability record so the requirement reads as decided rather than as skipped.
</planner_decisions>
