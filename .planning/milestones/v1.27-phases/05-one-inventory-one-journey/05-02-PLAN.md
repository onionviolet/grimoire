<planner_decisions>
Recorded so the executor does not re-litigate them.

- **Verified scope correction on the Foundry side of D-13.** The UI-SPEC's scope table and RESEARCH.md both state that no `failed` state and no `filtered to zero` state exist in the reviewed portrait surfaces. Reading `PortraitBrowse.tsx:280-364` directly shows otherwise: it already renders five distinct branches, `loading` (`foundry.loading`), `failed` (`foundry.error.title` through `EmptyState variant="error"` with a retry button and `CatalogDiagnostics`), `not indexed` (`foundry.portraits.notIndexed.*` with a browse-global action), `filtered to zero` (`foundry.portraits.filtered.*` with a clear-search action), and `catalog empty` (`foundry.portraits.empty.*`). RESEARCH.md's Open Question 3 asked for exactly this check before scoping new plumbing; the answer is that no plumbing is needed and no Foundry-side state is built. What is genuinely missing is on the **Locker** side, and that is what this plan builds. The Foundry branches are covered by an acceptance criterion so the verdict is recorded rather than asserted.
- **Where `filtered to zero` lives for portraits.** The Locker's family surface has no filter of any kind, so it has no filtered-to-zero state to build; inventing a filter to have something to empty would be scope invention. The portrait filtered-to-zero case is the Foundry one, already delivered. The Global inventory's own filtered-to-zero case is a different element and is built in plan 05-01.
- **How D-12 is delivered: adopt the existing helper, do not build a fifth table.** `PortraitBrowse.tsx:93-99` hand-rolls its hero options with a silent `?? code` fallback, which is precisely "silently attached to whatever label is at hand" that D-12 forbids. `buildHeroFilterOptions` already draws the distinction correctly and is already tested (`heroFilterOptions.test.ts`). Adopting it is the D-11 answer as well: one resolution path, consulted, not duplicated. `docs/portrait-alias-sweep-plan.md`'s own closing note anticipated this ("worth re-scoping once `heroFilterOptions.ts` lands, since it may already cover part of Leg B's reporting"); it has landed.
- **Where the neutral tag still earns its place.** The dropdown is hidden entirely in the hero-pinned workshop, and it does not exist at all when the catalog holds no unresolved codenames. The tag and its one-per-group hint therefore render above the family grid in the unscoped catalog view, one tag per distinct unresolved codename present in the visible set, so an unplaceable family is visible as a fact rather than as a card with a blank hero.
- **Leg A's genuine remaining gap.** `heroPortraitIdentity.test.ts` already carries an `alias table consistency` block, so Leg A is not unbuilt. Two real gaps remain: its `MISMATCHED` fixture covers twelve heroes where `ALIASED_PANORAMA` covers twenty-six, so the collision check runs on a subset; and nothing anywhere cross-checks the second live table (`lockerUtils.ts`'s display-alias collapse) against the roster. This plan closes both. It does not merge the two tables, because they answer different questions in different namespaces and merging them is a decision no source artifact makes.
- **Retry copy.** The failed state's action reuses `common.actions.retry` = "Retry", which the sibling Foundry surface already uses. The UI-SPEC directs reuse of `locker.pose.retry`; that key's value is "Retry preview", which would be wrong copy here. Documented deviation from the UI-SPEC copy contract, on the same grounds the contract itself gives for not inventing a second retry label.
