<objective>
Make the fork's engine story true on paper as well as in the release pipeline, add a guard that keeps the pin from drifting, and put the one half nobody can automate on the record honestly.

Purpose: the release workflow already checks out `onionviolet/vpkmerge` at a pinned commit SHA, builds it, and bundles it before packaging, and Settings already reports `vpkmerge 0.19.0 (798f3a7)`. Per D-02 that approach stays. The real gaps are that `scripts/fetch-vpkmerge.mjs` still describes itself as if the stock binary were the whole story, that nothing fails if the workflow's pin is ever loosened to a branch, and that the in-game colour half of the success criterion has no row anywhere.

Output: a reconciled header comment and engine policy, a new pin guard wired into the repo's existing gate block, and an engine-tier record row.

## Scope this plan deliberately does not take

Per D-02, this plan does NOT cut a GitHub Release on `onionviolet/vpkmerge`, does NOT add a cross-platform build matrix to that sibling repository, and does NOT change any code in `scripts/fetch-vpkmerge.mjs`. `VPKMERGE_VERSION`, the `ASSETS` table, and the sha256 verification stay byte-identical. Promoting a checksum-pinned fork release remains recorded future work, not silently dropped and not silently done.

Per Pitfall 1 in RESEARCH.md, this plan also does NOT build an engine version reporter or a Settings engine card. `foundry:engineInfo`, `EngineInfo`, and `ForkBuildCard` already exist and already work.

## Flagged planner assumptions (edge probe, unresolved)

- R1 / ordering: engine pinning produces no multi-element output, so there is no equal-element ordering contract to specify. No acceptance criterion written.
</objective>

| Boundary | Description |
|----------|-------------|
| CI runner to third-party repository | `.github/workflows/release.yml` checks out `onionviolet/vpkmerge` and executes `cargo build` on it. Whatever that ref resolves to runs with the runner's privileges and ends up inside the shipped installer. |
| dev machine to GitHub release assets | `scripts/fetch-vpkmerge.mjs` downloads a binary over https and installs it into `resources/vpkmerge/`. |
| packaged binary to capability attestation | `electron/main/services/foundryTextureReplace.ts` decides whether texture replacement is safe by reading a marker file, not by inspecting the binary. |
