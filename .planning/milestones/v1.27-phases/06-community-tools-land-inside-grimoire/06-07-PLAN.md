<objective>
Close the two findings the 2026-08-07 re-review (`06-REVIEW.md`) opened after 06-06 merged: CR-01, where accepting a captured browser-tool download always throws "Selected file is not a .vpk or supported archive" and therefore never installs anything, and WR-01, where that failure (and every other accept-time failure) is discarded in the renderer without a banner, a toast, or a log.

Purpose: 06-01 through 06-06 built every part of this path correctly except the join between two of them. `allocateToolDownloadTempPath` names the captured temp file with a neutral suffix; `importCustomModSource` checks the suffix before it ever sniffs bytes; the two have never met in a test because `electron/main/ipc/browser.test.ts` mocks the install function away. The result is that the flagship capability of this phase, ROADMAP Success Criterion 3's "the file reaches the mod library", fails on every accepted download, on every platform, and fails silently, which is why nobody noticed. WR-01 is why it was silent: the renderer already receives a populated `error` on every failure branch and throws it away.

Output: a captured download that a user accepts actually lands in the mod library, a regression test that exercises the real seam rather than a mock of one side of it, and an accept-time failure that is as loud as a refusal already is.
</objective>

## Decision: fix the naming side, not the gate side

The gate in `importCustomModSource` and the naming rule in `allocateToolDownloadTempPath` are two ends of one contract, and either end could be moved. This plan moves the naming end, for three reasons recorded here so the choice is visible rather than implicit:

- **It is lossless.** `classifyToolDownload` runs `checkVpkFile` on the completed file and refuses anything that is not a VPK *before* an entry is ever added to `state.pending` (`browserDownloadCapture.ts` lines 306 to 314). Nothing that is not a real VPK can ever be the subject of a disclosure, so naming the allocation with a VPK suffix states something that is always true by the time the path is used as an install source. It is not a widening of what the app will accept.
- **It costs no shared-file diff.** `electron/main/ipc/mods.ts` and `electron/main/services/extract.ts` are both listed in `docs/upstream-boundary-map.md` under "Shared and modified, in full", and `mods.ts` is seventh by churn against upstream. `06-CONTEXT.md`'s standing instruction for this phase is explicit that a fork-only file is preferred over a shared one whenever the same guarantee is reachable from there. `browserDownloadCapture.ts` is fork-only. The alternative fix, extracting the gate into a shared predicate in `extract.ts` and rewiring `mods.ts` to call it, would touch three shared files (`extract.ts`, `extract.test.ts`, `mods.ts`) to buy the same behavior.
- **It leaves the identity gate exactly where it was.** The gate that decides what a file *is* stays `checkVpkFile` at capture time and `resolveInstallableVpk` at install time, both magic-byte reads. This plan does not make the extension load-bearing; it makes the extension stop being an obstacle to reaching the code that does the real check. The head comment on the allocator is required by Task 1 to say exactly that, so a later reader does not conclude the suffix is a claim about the bytes.

**Reversibility of this choice: reversible.** If a future change makes the extension-first gate itself the thing worth refactoring, extracting a shared predicate later is purely additive and this plan forecloses nothing.

## Decision: the regression test calls the real install function

`06-REVIEW.md` asks for a test that calls the real `importCustomModSource` rather than the mock `electron/main/ipc/browser.test.ts` installs, and this plan does exactly that in a new fork-only test file. Two facts make it tractable rather than a research exercise, both verified during planning:

- Mocking every non-type relative import of `electron/main/ipc/mods.ts` (except `../services/extract`, which must stay real because it holds the identity gate) means no transitive module is loaded at all beyond `extract.ts`'s own dependency set, which `electron/main/services/extract.test.ts` already proves loads unmocked in this repo's vitest.
- The one non-relative value import, `@grimoire/social-types/heroes`, resolves through the pnpm workspace symlink and is already exercised under vitest by `src/lib/lockerUtils.test.ts`, so it needs no special handling.

The test asserts the seam and not a restatement of it: it builds its fixture path by calling the real `allocateToolDownloadTempPath`, so a future change to either the allocator's naming or the install function's gate fails this test instead of shipping.
