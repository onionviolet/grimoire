<planner_decisions>
Recorded so the executor does not re-litigate them. Each open item the source artifacts left unresolved is settled here with the alternative named beside it.

- **Option A, bake-then-disclose-at-Apply, is adopted.** 04-RESEARCH.md's Pattern 4 costed three options and recommended A. It is the only one that satisfies D-08's "exact normalized VPK paths" without a cross-repo change, and it costs nothing over what Apply already does because the disclosure reads back the same cache-keyed bake the apply performs. **Alternative recorded as reversible:** Option B, a live prefix scan of `particles/abilities/<codename>/` and `particles/weapon_fx/<codename>/` against `pak01`, is cheap enough to run while dragging sliders but misses the hand-curated texture, material and model entries for some heroes, so it could only ever be added later as an explicitly-labelled-approximate live indicator beside A's exact step, never as a replacement. Option C, a `vpkmerge --list-entries` flag, is out of boundary: it needs a change to the sibling Rust repository and a pin bump.

- **Research's proposed new `heroColors.ts` write-set function is not built, because phase 3 already shipped it.** 04-RESEARCH.md was written before `discoverRecolorEntries` and the `foundry:prepareRecolorStage` IPC landed. This plan consumes `foundryPrepareRecolorStage` from the renderer instead. That also moves 04-VALIDATION.md's `electron/main/services/heroColors.test.ts` Wave 0 gap: the write-set function it named does not need to exist, so the coverage it was asking for is satisfied by `recolorApplyConsequence.test.ts` plus the existing phase 3 coverage of the discovery path. Recorded here so a later validation audit does not read this as an unfilled gap.

- **Inline by default, blocking only when genuinely destructive.** RESEARCH.md Open Question 1's recommendation, adopted. The disclosure renders inline beside the action, in the panel, and the write proceeds in the same press for the routine case, which is what D-07's "routine non-conflicting actions keep their current speed" asks for. A second explicit press is required only when the disclosure shows that an enabled source other than Grimoire's own managed artifacts currently wins one or more of the paths the recolor would take over. **Reversible alternative:** raising the gate to every apply is a one-line change to the predicate in the pure module.

- **The confirm gate is re-armed by any parameter change.** The gate remembers the exact serialized export request it disclosed. Moving a slider produces a different request and therefore a different write set, so a previously granted confirmation must not carry over.

- **Grimoire's own Locker-managed artifacts must not contest the user against themselves.** The managed ability-colours VPK is a scanned mod like any other, so a hero with a recolor already applied would otherwise trip the confirm gate on every re-apply against its own previous output. Rather than name-matching a metadata string in the renderer, this plan adds a `lockerManaged` boolean to `FoundryAssetSource`, set from the four `locker*` metadata markers that main already uses for exactly this classification. It is additive, it mirrors the existing `managed` field, no existing reader changes, and it is honest on its own terms: `AssetSourcesPanel` currently labels the Locker's own auto-rebuilt output `Third-party` on every surface that renders it.

- **`provenance()` is left alone.** Widening its `Forged` branch to swallow Locker-managed artifacts would have been one line, but `Forged` also means "a mod the user forged themselves", which SHOULD contest a recolor. Conflating the two would silently suppress a warning the user wants.

- **The Body plus Gun trippy panel is out of scope.** `TrippySkinPanel` writes the separate material-texture slot through `applyTrippySkin` (`trippyEffects.ts`, pak04), not the ability particle slot. RESEARCH.md costed Option A against `applyHeroColor` / `applyHeroPrism` / `applyHeroTrippyVfx` only, and no equivalent discovery path exists for the materials slot. Left as a stated boundary rather than an assumed inclusion.

- **UI-SPEC E6's `error` row stays a backstop.** A `loadMods()` failure and a load in progress render identically as the neutral dot, because both mean the count is unknown. Nothing in CONTEXT.md decides otherwise.
</planner_decisions>
