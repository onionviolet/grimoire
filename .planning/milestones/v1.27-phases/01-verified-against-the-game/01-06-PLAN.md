Create `scripts/check-verification-record.mjs` following the shape of `scripts/check-encoding.mjs`: pure exported functions plus a CLI entry guarded so importing the module runs nothing.

Export two functions:

- `parseVerificationRecord(text)` - reads the markdown, finds the pipe tables, keys each table's schema off its header row, and returns the rows as records with their cells trimmed. It must not care about column order beyond the header telling it which cell is which.
- `checkVerificationRecord(text, options)` - runs the rules below over the parsed rows and returns a result carrying the problems found plus counts of total rows, filled verdicts, and blank verdicts. `options.strict` selects the completion gate.

Two row schemas, distinguished by their header row:

- Check rows, used by the sweep and rigged-preview tables, with the header cells: ID, Check, Fixture, Steps, Pass looks like, Verdict, Evidence, Root cause.
- ConVar rows, used by the readings table, with the header cells: ID, ConVar key, How to read, Reading, Verdict, Notes.

The rules, all of which come straight from the CONTEXT decisions:

1. Row inventory. Exactly these 41 IDs appear, each exactly once, no others: IG-01 through IG-22, RP-01 through RP-03, CV-01 through CV-16. A missing ID and a duplicate ID are both errors. Hold the expected inventory in the script so a row silently deleted from the doc is caught.
2. Scaffold completeness (D-09). On a check row, the Check, Fixture, Steps, and Pass looks like cells are all non-empty. On a ConVar row, the ConVar key and How to read cells are non-empty. These are what the plan fills in; only the verdict is the human's.
3. Verdict vocabulary (D-10). A non-empty Verdict cell is exactly one of `pass`, `fail`, or `blocked`. Anything else is an error, so a half-typed note cannot read as a verdict.
4. Evidence (D-08). A `fail` verdict requires a non-empty Evidence cell on a check row, or a non-empty Notes cell on a ConVar row. A pass needs no attachment, because the written verdict is the evidence.
5. Root cause (D-11). A `fail` verdict requires a non-empty Root cause cell on a check row, or a non-empty Notes cell on a ConVar row. The note comes before any fix-here-versus-new-phase call.
6. Blocked reason (D-10). A `blocked` verdict requires a non-empty Root cause cell on a check row, or a non-empty Notes cell on a ConVar row. Blocked is legitimate; blocked without a reason is not.
7. Reading present. A ConVar row whose Verdict is `pass` requires a non-empty Reading cell. A recorded pass with no number recorded nothing.
8. Completion gate (D-10), only under `strict`. Zero blank Verdict cells. Without `strict` a blank verdict is fine, which is what lets the repository suite stay green while the record is still being filled.

The CLI defaults its target to `docs/ingame-verification-record.md` relative to the repository root, accepts an explicit path argument, accepts `--strict`, prints a one-line summary carrying the total row count and the filled and blank verdict counts, prints each problem it found, and exits 1 when any rule failed. Do not add an npm script for it: the phase's standing constraint is to keep shared-file edits to a minimum and `package.json` already carries this phase's one dependency line.

Then create `scripts/check-verification-record.test.ts`, importing the two exported functions the way `check-encoding.test.ts` imports its own. Build every fixture as a small inline markdown string from a local factory function with overridable cells, matching the repo's inline-factory convention; do not read the real record doc, which would couple the guard's tests to the doc's current fill state.

Cover, at minimum: a well-formed complete record passing both non-strict and strict; a record with a blank verdict passing non-strict and failing strict; a missing ID; a duplicate ID; an unknown verdict word; a `fail` with no evidence; a `fail` with no root cause; a `blocked` with no reason; a check row with an empty Steps cell; a ConVar row marked pass with no reading; and a mixed record where both schemas appear and both are parsed correctly.

Keep the script pure ASCII where practical and run the encoding gate, since `pnpm encoding:check` scans `scripts/`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| human observation -> committed record | A verdict typed by a person becomes the project's evidence of correctness |
| record doc -> git history | The file is committed and read later as ground truth by planning and audit |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-01-17 | Spoofing | verdict cells in the record | high | mitigate | A fabricated pass is the one failure that would defeat this entire phase. | T-01-18 | Repudiation | failed checks with no root cause | medium | mitigate | The guard rejects a `fail` with no root cause and a `blocked` with no reason, so a failure cannot be recorded in a form that leaves nothing to act on later. |
