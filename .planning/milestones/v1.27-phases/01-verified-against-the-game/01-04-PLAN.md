The round trip itself (D-05):

1. Read the bundled template through `readChatWheelStarter()` rather than reading the file path directly, so the `chat-wheel:starter` half of the requirement is exercised through its real accessor.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test process -> bundled `ChatLane.exe` | A child process is spawned with two filesystem paths as arguments |
| YAML fixture -> converter | Untrusted-shaped text crosses into a native binary |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-09 | Tampering | `readChatWheelVpk` input path | medium | mitigate | Task 2 asserts the existing extension-and-existence guard rejects a non-`.vpk` and a missing path before `runChatLane` spawns anything, so the guard is under test rather than assumed. |
| T-01-10 | Tampering | `buildChatWheelVpk` temp directory lifecycle | medium | mitigate | Task 1 asserts `cleanup()` removes the built VPK and Task 2 asserts a failed build leaves no directory, so a converter failure cannot strand attacker-influenced bytes on disk. |
| T-01-11 | Elevation of privilege | `spawn(ChatLane.exe, [input, output])` | medium | accept | Both arguments are paths the service itself created under `mkdtemp(tmpdir())`; no user string reaches argv, the spawn passes an argument array rather than a shell string, and `windowsHide` is already set. This plan changes none of that.
