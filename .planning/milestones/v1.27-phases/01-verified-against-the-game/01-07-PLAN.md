<objective>
Turn the rigged hero preview from an arithmetic estimate into a release decision.

Purpose: `docs/rigged-preview-spike.md` section 6 produced a frame-budget figure by arithmetic and labelled it as one. Section 9 says outright that no fps measurement exists and that check 3 of section 8 is the blocker on defaulting the rigged path on. Section 9's next step 1, decoupling rigged from cloth, already shipped: `heroPoseRenderFeatures.ts` gives rigged its own flag and `HeroPoseViewer.test.ts` asserts the decoupling. Next step 2 is this plan.

This was a blocking human checkpoint until 2026-08-06. It is not one any more. The measurement needs a GPU and a running build, but not a person: `scripts/dev-driver.mjs` reaches the live renderer over CDP, so a rAF sampler under each flag state is a script. The decision it feeds was never the hard part. Flipping a module constant behind an already-decoupled flag is a one-line, fully reversible change: no on-disk format, no published contract, no dependent system. What remains human is the judgment that the machine the reading came from is representative, which is why the record now names the GPU.

Output: `RELEASE_RENDER_FLAGS.rigged` set to what the measurement argues for, the recommendation written into `docs/ingame-verification-record.md`, and the spike's own next-step list marked resolved.
</objective>

Take the reading. This is no longer a human checkpoint: `scripts/dev-driver.mjs` reaches the live renderer, so the sampler is a script.

Start a dev slot nobody else is attached to and confirm it with `node scripts/dev-driver.mjs eval "window.__GRIMOIRE_DEV_SLOT"`. Never use slot 0 for this.

Open Seven's Locker hero page and wait for the preview canvas to exist before sampling, rather than sleeping a fixed number of seconds. Set cloth off for both runs so the reading measures the animated path and nothing else.

Sample with `requestAnimationFrame`, collecting frame timestamps for ten seconds per run, and take the median of the deltas. Not the average: the spike says median explicitly, because one compositor hitch moves an average and does not move a median. Run static first, then rigged, at the same hero and the same window size, and read `window.devicePixelRatio` for the record.

Discard the first second of each run. A freshly mounted three.js scene is still compiling shaders and uploading textures, and those frames are not the steady state the bands describe.

Then apply the bands from spike section 8 check 3 mechanically, without interpretation:

- delta within about 1 ms of static: ship, and Task 3's roster sweep runs
- delta 1 to 3 ms worse: investigate, which resolves to gated for the flag
- delta more than 3 ms worse, or any run below 30 fps: fail, which resolves to gated
- a delta landing exactly on a band edge goes into the more conservative band

Write RP-03 with the two medians, the delta, the dpr, the band, the sample counts, and the GPU and OS the reading was taken on. That last item matters and the spike does not currently ask for it: the bands were written for mid-range hardware, and a delta measured on a much faster or much slower card is not the same evidence. Name the machine so a later reader knows what the number is a fact about.

If the canvas never appears, or the rigged flag cannot be set at run time, record RP-03 as `blocked` with the reason and leave the flag alone. Do not fall back to an estimate.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| driver measurement -> release flag | A frame-time reading taken on one developer machine changes what shipped builds render for everyone |
| game pak file -> vpkmerge sweep | The app's detected game path is passed to a bundled native tool on the ship branch |
| record doc -> git history | The measurement and the recommendation become the project's justification for the flag |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-21 | Spoofing | `RELEASE_RENDER_FLAGS.rigged` | high | mitigate | Moving a release flag on a number nobody measured is the exact failure this requirement exists to prevent. Mitigated by the plan prohibition against moving the flag on an estimate, by requiring the two medians, the delta, the dpr, and the sample counts in the record beside the flag value, and by the band rules being applied mechanically rather than argued. |
| T-01-29 | Spoofing | one machine's reading generalized to every user | medium | mitigate | The bands were written for mid-range hardware, and a driver run happens on whatever card the developer has. Mitigated by recording the GPU and OS beside the reading, so a `ship` verdict taken on a fast card is visibly a fact about that card. A reading on hardware materially faster than mid-range is recorded as such and the ship branch is not taken on it alone. |
| T-01-22 | Denial of service | rigged preview enabled for every user | medium | mitigate | The band thresholds from spike section 8 check 3 are the gate: a delta worse than about 1 ms or any drop below 30 fps resolves to gated, so a preview that degrades mid-range hardware cannot be enabled by this plan. The doubled per-hero cache cost is named in the ship option's cons so the choice is made with it in view. |
