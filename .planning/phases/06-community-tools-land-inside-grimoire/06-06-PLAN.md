## Decision: move the subscriber, do not build a replay

06-VERIFICATION.md `missing` offered two routes. This plan takes the first (move to an app scoped subscriber) and explicitly declines the second (a main process replay or reconciliation of a still pending disclosure). The reasoning, recorded here so it is visible rather than implicit:

- After the move, the subscriber's lifetime is the renderer document's lifetime, not a route's mount. Every window CR-01 actually describes closes: the tool takes seconds to build, the user wanders to Installed, the push lands, and it is handled.
- The window the move does not close is "no renderer document exists at all". Two cases, and neither wants a replay:
  - **App restart.** `state.pending` in `browserDownloadCapture.ts` is an in memory `Map`. After a restart there is nothing to replay: the entry is gone by construction. Making it replayable would mean persisting a pending disclosure, derived from guest originated bytes, across sessions, and then asking the user on next launch about a file they may no longer connect to anything they did. That contradicts D-09 (where the file goes is decided, not asked) and adds durable state to a path whose whole trust story is that it holds at most one transient file. The correct answer for this case is Task 2's sweep: the orphan is deleted and the system is left exactly as if the capture had never happened. Nothing was written to the mod library, because only an accepted confirm writes.
  - **Renderer reload or crash.** The main process keeps the pending entry while the renderer document is replaced. The exposure is the interval between `will-download` and the `ready` push, which for a client side built blob is sub second, and it requires the user to reload the window or the renderer to crash inside that interval. A mount time pull would cover it at the cost of a new IPC channel, a new preload method and a new type on two shared and modified files (`electron/preload/index.ts`, `src/types/electron.ts`). Not worth it for that window, and the sweep still cleans up after it.
- **Reversibility of this choice: reversible.** Adding a pull based reconciliation later is purely additive: one `ipcMain.handle`, one accessor over the existing pending map, one preload method, one call in the hook's mount effect. Nothing in this plan forecloses it.

The residual window is therefore stated, bounded and mitigated, not denied. Task 3 records it in `docs/browser-scope-boundary.md` so the document stops overstating the invariant.

  <action>
In `electron/main/services/browserDownloadCapture.ts`, add two exports beside the existing pending map helpers.

`pendingToolDownloadPaths(): string[]` returns the `tempPath` of every entry currently in `state.pending`. It is the path shaped sibling of the existing `pendingToolDownloadIds`, and it exists so the sweep can state its safety rule in terms of live entries rather than trusting a caller to know.

`sweepToolDownloadTempRoot(root: string, protectedPaths?: Iterable<string>): Promise<number>` deletes orphaned captured downloads and returns how many it deleted. It takes the root as a parameter for the same reason `toolDownloadTempRoot` does: so it is testable without `app`. When `protectedPaths` is omitted it defaults to `pendingToolDownloadPaths()`, so the safety rule is the default rather than something a call site has to remember.

Write the retention rule and the safety rule as a head comment on that function, in these terms:

Retention rule: a captured temp file is retained only for as long as its id is in the in memory pending map, and that map never survives the process. Every regular file present in the root at process start is therefore orphaned by construction, so the sweep deletes all of them. There is deliberately no age threshold and no size cap: an age threshold would only delay a deletion that is already provably safe (the sweep runs from app.whenReady, before any window has loaded a renderer, so no capture can be in flight), and the directory holds at most one live file at a time by the single pending invariant.

Safety rule, four parts, all of which the implementation must actually enforce rather than merely assert: it never deletes a path present in the protected set; it reads only the direct entries of the root via readdir with withFileTypes and deletes only entries whose dirent reports isFile, so a directory or a symbolic link entry is skipped and never followed (withFileTypes uses lstat semantics, so a link to a file reports isFile false); it never recurses; and it builds every deletion path as join(root, dirent.name) from the dirent's own name, never from a suggested filename that came from the guest. A skipped non file entry is logged once with console.warn so an unexpected entry is visible rather than silent.

Failure handling matches `runPoseCacheSweep`: a missing root returns 0 rather than throwing, and a per entry unlink failure is caught, logged with the existing `[BrowserDownloadCapture]` prefix, and does not stop the remaining entries. The function never throws.

Path comparison against the protected set is plain string membership in a Set. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| guest webview to main | Untrusted, guest originated bytes and a guest suggested filename cross here on `will-download`, and are written to a Grimoire owned temp path |
| renderer to main | `browser:resolve-tool-download` decides whether a temp file is installed into the mod library; the renderer names the id |
| filesystem to main | The startup sweep enumerates and unlinks entries under the userData browser-downloads directory, which is a destructive operation on whatever it finds there |
| main to renderer | The disclosure push now reaches an app shell subscriber that can raise a modal over any page, not only the page that started the download |
