# Phase 06 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none (hand-rolled primitives over React + Tailwind 4; no Radix/base-ui) |
| Icon library | lucide-react |
| Font | `--font-radiance` (app body/UI face); no new display-font usage this phase |

**shadcn gate resolved as "no" without an interactive prompt, on codebase evidence, not by default:** `components.json` is absent, but the project is not designless. `docs/ui-conventions.md` documents a mature, actively-enforced hand-rolled system (tokens in `src/index.css` `@theme`, primitives in `src/components/common/{ui,forms,PageComponents,Modal,menu,ToastStack,Skeleton}.tsx`), and it is a lint-adjacent house rule ("reach for an existing primitive before writing markup... tokens instead of raw values"). Introducing shadcn now would run two parallel design systems inside one app for a phase whose own standing instruction is "least code, prefer the cheap side of the upstream boundary." This phase's new elements (catalog kind groups, pre-write disclosure, refusal banner) are built entirely from existing primitives (`Tag`, `Button`, `IconButton`, `ConfirmModal` via `useConfirm`, `ToastStack`, `SectionHeader`) — no new component-library dependency is warranted. If a future phase wants to evaluate shadcn wholesale, that is a project-level decision, not one this phase should force by default.

## Spacing Scale

This phase adds no new page and no new layout region — it extends `Browser.tsx`'s existing toolbar/shortcut-row/webview-frame layout and reuses `ConfirmModal`. Declared values below are the actual tokens already load-bearing in the surfaces this phase touches (Tailwind's 4px step, per `docs/ui-conventions.md`):

| Token | Value | Usage |
|-------|-------|-------|
| 2xs | 2px | `Tag`/`Badge` vertical padding (`py-0.5`) — existing exception, not new |
| xs | 4px | Icon-to-label gaps inside buttons/banners (`gap-1`) |
| sm | 6-8px | Compact control spacing: shortcut-row gap (`gap-1.5`), toolbar button gap (`gap-2`), `Tag`/`Badge` horizontal padding (`px-1.5`/`px-2`) |
| md | 12-16px | Banner/confirm-modal internal padding (`px-3 py-2` for the inline banner, `p-6` for `ConfirmModal`'s panel is unchanged, not touched this phase) |
| lg | 24px | Section gap between the toolbar row, the new kind-grouped shortcut rows, and the webview frame (`gap-3`→ round up to the 24px band when a group header is inserted; keep `gap-3`/12px between rows within one kind group, `gap-4`/16px between kind groups) |

Exceptions:
- `Tag`/`Badge` compact padding (2px/6px) is a pre-existing house exception for HUD-style status chrome, not something this phase introduces — do not "fix" it to the 8-point scale.
- No new spacing values are needed beyond what `Browser.tsx`, `Tag`, `SectionHeader`, and `ConfirmModal` already define.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-bg-primary` `#0f0f0f` | App/page background behind the toolbar, shortcut rows, and webview frame |
| Secondary (30%) | `--color-bg-secondary` `#1a1a1a` / `--color-bg-tertiary` `#242424` | Webview frame border+bg, address bar input, existing toolbar buttons, shortcut-row buttons — unchanged |
| Accent (10%) | `--color-accent` `#f97316` | Reserved for exactly three new elements — see below |
| Destructive | `--color-state-danger` `#f87171` | Refusal banner only — see below |

Accent reserved for:
1. The disclosure's primary CTA button (`Add to library`), styled with the existing `Button variant="primary"` (`border-accent/40 bg-accent/10 hover:bg-accent/20`).
2. The `Tools` kind-group header/label, so the one destination that can hand a file to Grimoire reads as distinct from `Mod hosts`/`Reference`/`Community` at a glance — no other kind group takes accent.
3. Focus rings on the two new interactive controls introduced (the confirm dialog's buttons, which already use `focus-visible:ring-accent` via `ConfirmModal` — no new focus-ring color is invented).

Explicitly NOT accent: the existing back/forward/reload/home toolbar buttons, the address bar, and the `Mod hosts`/`Reference`/`Community` group headers all stay on the neutral `text-text-secondary`/`border-border` palette exactly as today — this phase does not repaint existing chrome.

Destructive reserved for: the refusal banner shown when `checkVpkFile` rejects a browser-produced download (danger-tone `Tag`/banner, matching the existing NSFW `18+` `Tag tone="danger"` precedent and the existing `failure` banner's `border-warning/40` pattern, upgraded to danger since a refused file is a harder stop than a load failure). Not used for the `Discard` button (declining an unconfirmed download is a neutral action, not a destructive one against existing user data) — `Discard` uses `Button variant="secondary"` (neutral), matching `ConfirmModal`'s existing cancel-button styling.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | **Add to library** — `useConfirm({ confirmLabel: t('browser.toolDownload.confirm', 'Add to library') })`. Deliberately not the generic "Confirm": matches D-09's own phrasing ("added to your mod library as `<name>`") and the house pattern of a specific verb+noun confirm label (`Rebuild`, `Stage anyway`, `Delete`) seen throughout `foundry/*.tsx`. |
| Secondary action | **Discard** — `cancelLabel: t('browser.toolDownload.cancel', 'Discard')`. Not "Cancel": cancelling here has a concrete side effect (the temp file is deleted), and "Discard" says that plainly rather than implying nothing happens. |
| Disclosure title | `browser.toolDownload.title`: **"Add this download to your mod library?"** |
| Disclosure body | `browser.toolDownload.message`: **"Will add to your mod library as "{{name}}"."** — same shape as the existing `buildTray.willCreate` precedent (`"Will create: {{name}}.vpk"`), parameterized identically. `{{name}}` falls back to a fixed default (see Copy Fallback row) rather than ever rendering blank. |
| Copy fallback (no usable filename) | `browser.toolDownload.fallbackName`: **"Browser download"** — used when `item.getFilename()` yields an extensionless/generic Chromium default (Pitfall 4); never shown to the user as the raw Chromium filename without this fallback available. |
| In-flight toast | `browser.toolDownload.downloading`: **"Downloading from {{tool}}..."** (info tone, `ToastStack`) — shown from the moment `will-download` fires for a `kind: 'tool'` destination until the disclosure (or refusal) appears, so the gap between clicking `Build VPK` and seeing a dialog is never silent. |
| Replaced-pending toast | `browser.toolDownload.replaced`: **"Replaced with a newer download from {{tool}}."** (info tone) — shown when a second tool download starts while an earlier one's disclosure is still unanswered (see UI Considerations, zero-one-many row). |
| Error state (refusal banner) | `browser.toolDownload.refusedPrefix`: **"Not added: "** prepended to the main-process `describeVpkRejection()` string verbatim (e.g. "Not added: Pimp My Hideout download is a ZIP archive, not a VPK. Deadlock cannot load it."). The reason clause itself stays main-process English text per existing precedent (VPK rejection strings are not i18n-wrapped anywhere in the codebase today — `checkVpkFile`/`describeVpkRejection` run in the main process, which has no i18n context); only the static prefix and banner chrome are translated. Danger-tone banner, same visual shape as the existing `failure` paragraph in `Browser.tsx` (`rounded-sm border ... px-3 py-2 text-xs`), upgraded to `border-state-danger/40 bg-state-danger/10 text-state-danger`. Shown before any confirm step — the confirm dialog is never shown for a refused file. |
| Destructive confirmation | Not applicable this phase. No delete/overwrite action is introduced: per D-01/D-02 the confirmed download becomes an ordinary third-party mod, and disabling/deleting it later goes through Installed's existing, unmodified confirm flow. Do not add a second destructive-confirmation surface here. |
| Kind-group headers | `browser.catalog.groups.modHost`: **"Mod hosts"** · `browser.catalog.groups.tool`: **"Tools"** · `browser.catalog.groups.reference`: **"Reference"** · `browser.catalog.groups.communityFeed`: **"Community"** — rendered in that order (Mod hosts first, matching today's GameBanana-first convention; Tools second, since it is the capability this phase adds and deserves visibility, not buried last). |

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5) and lifted by plan-phase's
> `## UI Considerations` lift rule via the identical rule as SPEC `## Edge Coverage`. Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text).
> Empty-state and error-state COPY live in `## Copywriting Contract` above — this section covers
> state coverage and REFERENCES those rows rather than restating the copy (de-dup).

Applicable state considerations resolved: 6 covered, 3 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Catalog kind-groups (list-collection) | ✅ covered | A kind group with zero entries after the D-07 per-URL review renders nothing at all — the group header itself is omitted, never an empty-group placeholder or a "no entries" message. |
| populated | Catalog kind-groups (list-collection) | ✅ covered | Each kind group reuses today's exact `flex flex-wrap gap-1.5` shortcut-row rendering, one row per kind, unchanged from the current single-row layout. |
| zero-one-many | Catalog kind-groups (list-collection) | ✅ covered | A kind with exactly one entry (`Tools` holds only Pimp My Hideout at launch) renders as a single button in its own group — no singular/plural copy variant needed since group headers are fixed labels, not counts. |
| overflow | Catalog kind-groups (list-collection) | ✅ covered | Existing `flex-wrap` on the shortcut row absorbs any number of entries per kind at any window width; no horizontal scroll or clipping is introduced. |
| long-text | Catalog entry labels (nav) | 🧪 backstop | Catalog labels are curated short strings (all current entries ≤ 21 chars). No truncation styling is added; a longer label wraps via the row's default `flex-wrap` rather than truncating. Verify at execution time that no post-D-07-review label forces a shortcut button onto two lines at the narrowest supported sidebar-collapsed window width. |
| loading | Pending tool-download disclosure (interactive-control) | 🧪 backstop | Between `will-download` firing and the disclosure (or refusal banner) appearing, the `browser.toolDownload.downloading` info toast is shown (Copywriting Contract), so the click-to-dialog interval is never silent. Needs an execution-time check that the toast actually appears before the temp-file write completes, not just that the string exists. |
| error | Pending tool-download disclosure (interactive-control) | ✅ covered | A file `checkVpkFile` rejects is refused before any confirm step, via the danger-tone refusal banner (Copywriting Contract, Error state row); the confirm dialog is never shown for a rejected file. |
| zero-one-many | Pending tool-download disclosure (interactive-control) | 🧪 backstop | Only one pending tool-download disclosure exists at a time. A second `Build VPK` click while an earlier disclosure is unanswered discards the earlier pending temp file and replaces it with the new one, surfaced via the `browser.toolDownload.replaced` toast (Copywriting Contract). This resolves Open Question / Pitfall 4's collision risk with a "replace-newest" policy; needs a held-out test asserting the stale pending id is ignored if resolved after replacement (mirrors the confused-deputy mitigation already named in RESEARCH.md's Security Domain). |
| long-text | Refusal banner reason text (static-content) | ✅ covered | Uses the existing `failure` banner's plain-paragraph wrap (no `truncate`/`nowrap`), identical to today's page-load-failure banner; `describeVpkRejection()` strings are single sentences and wrap normally at the banner's existing width. |
