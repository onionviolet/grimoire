  <action>
Create `src/lib/browserCatalog.reachability.test.ts`. It imports `BROWSER_DESTINATIONS` from `./browserCatalog` so there is exactly one URL list in the repo. Wrap the whole suite in a guard that skips unless `process.env.GRIMOIRE_CHECK_DESTINATIONS` is set, using vitest's `describe.skipIf`, because the default `pnpm test` run and CI must not depend on nine third-party sites being up. State that reason in a comment at the top of the file.

For each destination the suite performs one `fetch` with `redirect: 'follow'` and a 15 second `AbortSignal.timeout`, and records four facts: the HTTP status, `response.url` (the final address after redirects), the `<title>` text extracted from the first 8 kilobytes of the body with a non-greedy regex, and whether the final URL's host differs from the requested host. It asserts nothing beyond `status < 400` for an entry the catalog still claims is live; the point of the run is the record it prints, not a pass or fail. Print each row with `console.log` in a fixed-width, copy-pasteable form so the results can be transcribed into the doc without rerunning.

Add one extra probe pair outside the catalog loop, for the specific question REQ-browser-tool-catalog names: request `https://deadlocked.wiki/` and `https://deadlock.wiki/` and print both rows. Do not assume either answer.

Run the probe: `GRIMOIRE_CHECK_DESTINATIONS=1 pnpm exec vitest run src/lib/browserCatalog.reachability.test.ts`. If the environment has no outbound network access, do not guess and do not fabricate a row. Record the failure honestly in the doc as `unreachable from this environment` for every entry, and say so in the SUMMARY so the checkpoint in task 2 can be answered by a human who does have network access.

Create `docs/browser-destinations.md`. Structure: a short preamble stating what this file is (the record REQ-browser-tool-catalog and ROADMAP phase 6 success criterion 1 ask for), how it was produced (the command above), the date it was produced, and an explicit sentence that these are third party sites Grimoire links to and does not endorse, vet, or vouch for. Then a table with one row per destination: Label, Declared kind, Requested URL, Status, Final URL, Page title, Host changed, Proposed verdict. Then a short section for the `deadlocked.wiki` against `deadlock.wiki` finding, quoting both rows. Then a section recording D-06's decision that no crosshair generator entry is added, with its reason. Then a section naming any entry the evidence does not settle, with the specific question a human needs to answer.

Verdict rules, applied mechanically so the proposal is evidence-driven rather than taste-driven:
- Status under 400 and the final host equals the requested host and the title plausibly matches the label: propose keep.
- Status under 400 but the final host differs from the requested host: propose correct, with the final URL as the replacement.
- Status 400 or above, a DNS or connection failure, or a title matching a parked or domain-for-sale page: propose remove.
- Anything the evidence leaves genuinely ambiguous, including a title that does not obviously match the label: propose needs a human call, and write the exact question.

Do not edit `src/lib/browserCatalog.ts` in this task. Recording and deciding are separate steps on purpose.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| catalog URL to the guest webview | Every URL in this list is a page Grimoire will load, on the user's behalf, in a browser inside their mod manager |
| catalog `kind` to the download capture gate | The `tool` kind is a capability grant, so which entry carries it is a security decision, not a labelling one |
| probe fetch to a third-party host | The reachability run makes outbound requests from a developer machine |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-16 | Spoofing | a lapsed or repointed catalog domain | high | mitigate | Every entry is probed for its final resolved host and page title, and any entry that fails, redirects off its own host, or serves a parked page is corrected or removed rather than kept. The record is dated so its staleness is visible. |
| T-06-17 | Elevation of Privilege | which entry carries `kind: 'tool'` | high | mitigate | Exactly one entry gets `tool`, and it is the one the phase was scoped around. The doc records the kind per entry, so granting capture to a second destination is a visible, reviewed change rather than a quiet edit. |
| T-06-18 | Tampering | probe result transcription | medium | mitigate | The probe imports the live catalog rather than a copied list, and the doc records the exact command and date, so a claim in the table can be re-derived instead of trusted. |
| T-06-19 | Information Disclosure | outbound probe requests | low | accept | The probe is opt-in behind `GRIMOIRE_CHECK_DESTINATIONS`, never runs in CI or in the shipped app, and requests only public homepages that the app already loads in normal use. |
| T-06-SC | Tampering | npm/pip/cargo installs | high | accept | No packages are added by this plan. RESEARCH.md's Package Legitimacy Audit records zero new dependencies, so there is no install task to gate. |
