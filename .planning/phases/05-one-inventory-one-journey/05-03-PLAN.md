<planner_decisions>
Recorded so the executor does not re-litigate them.

- **Which bulk mutations D-14 and D-15 apply to, decided.** This was RESEARCH.md's sharpest open question and its Assumption A5. The answer: the five reversible bulk handlers that already exist in `src/pages/Installed.tsx` (bulk enable, bulk disable, bulk hero tag, bulk clear tag, bulk global tag). Bulk delete is excluded because it is destructive and a snapshot of store state cannot bring a deleted VPK back; it keeps its existing confirmation, which is the correct affordance for it.
- **Why not build bulk selection into the Global shell first.** That was the other defensible option and it is rejected. `Locker.tsx` has no multi-select of any kind today, so taking that path would mean inventing a brand-new bulk surface purely so the undo requirement had something to attach to, which is backwards: the success criterion is "any bulk action can be undone without rebuilding the selection by hand", and it is satisfied against real surface only where bulk actions really exist. It would also put a second mature multi-select implementation in the tree, which is exactly the two-homes failure this phase exists to end. If a Global-shell bulk action is ever added, it inherits this module rather than growing its own.
- **What the snapshot holds, and why not more.** Three fields per mod: `enabled`, `lockerHero`, `globalType`. Those are the only fields the five handlers write, they are already in the Zustand store, and capturing them is a `Map`-shaped read rather than a subsystem. Priority and load order are deliberately not captured: no bulk handler writes them.
- **Restore replays a diff, not the whole snapshot.** `bulkUndoPlan` compares the snapshot against the live mods and emits an operation only for a field that actually differs now. That is what stops an undo from stomping a change the user made by hand between the batch and the undo, and it is why `toggleMod` being a flip rather than a set is safe to use.
- **One toast, not two, for a partial failure.** This settles the UI-SPEC's E6 `error` backstop and RESEARCH.md's Assumption A4. Two simultaneous toasts for one user action reads as two unrelated events. The single message names the changed count and the count that could not be changed, and it keeps the Undo action, because the changed subset is still reversible.
- **Blocker exposure through an accessible description pointing at rendered text.** D-16 permits "beside the control or through an accessible description" and forbids tooltip-only. The action bar already renders one in-flight line while a batch runs; this plan gives that line a stable id, extends it to cover the undo-in-flight case, and points every control disabled by that state at it with `aria-describedby`. That satisfies both halves at once and adds no new layout.
- **One reason at a time.** When both an undo and a batch could theoretically be in flight, the undo wins the message, matching how error states elsewhere in the app avoid stacking simultaneous explanations.
</planner_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer to main (IPC) | A restore replays mod ids and tag values through `toggleMod`, `setModLockerHero` and `setModGlobalType`, the same channels the batch itself used |
| renderer state to disk | A restored enable or disable rewrites the mod load order on disk through the existing toggle path |
