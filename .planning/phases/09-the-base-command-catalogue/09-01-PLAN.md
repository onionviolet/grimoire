(Prerequisite fix, in scope for this task: the custom_menus end-scan currently swallows column-0 comments and the trailing empty line after the block; it must stop after the last indented non-blank line, see the action block for why "non-blank" and not "non-comment".)
    - Robustness: an override-block line the entry regex does not match (wrong value casing like `TRUE`, an anchor, a stray comment mid-block) is preserved verbatim; it never enters the model and is never deleted by an update, even when neighbouring entries are toggled or removed.
    - Update, one toggle: changing one entry's boolean rewrites only that entry's value token; the key text keeps its original quoting style and every other line is byte-identical.
    - Update, add: a key added to a populated block appends one line immediately after the block's last entry line (not after interior or trailing comment lines, which stay in place), serialized plain when the key is safe per overrideKey below, else JSON-quoted. Adding to an inline `{}` map rewrites that one line into a block header plus one entry line.
    - Update, remove: removing an entry deletes exactly its line. Removing the last entry collapses the block to `override_bindable: {}` (matching starter style); the collapse removes only parsed entry lines, never preserved unparsed or comment lines (if any such lines remain, the block header stays). A model map of `undefined` removes the whole block if present, and writes nothing if absent.
    - Update, create: a defined model map with no existing block appends the block at the end of the file (header plus entries, or `key: {}` when empty).
    - `overrideStateFor(map, id)` returns `'inherit'` when the map is undefined or lacks the key, `'on'` for true, `'off'` for false.
    - `applyOverride(model, 'bindable' | 'pingWheel', id, state)` returns a new model: `'on'`/`'off'` set the boolean (creating the map if undefined, preserving insertion order); `'inherit'` deletes the key (an emptied map stays `{}`, never reverts to undefined).
  </behavior>

  <action>
Extend `ChatWheelModel` with `overrideBindable?: Record<string, boolean>` and `overridePingWheelBindable?: Record<string, boolean>`.

In `parseChatWheelYaml`, after the existing menu parse, parse each map with a shared helper `parseOverrideMap(lines, rootKey)`: find the line matching `^<rootKey>:\s*(.*)$` at column 0; if absent return undefined; if the rest (comment-stripped) is `{}` return {}; otherwise scan following lines using the same stop rule as the menu parser (stop at the first non-indented, non-comment line), collecting entries matching indented `key: true|false` with an optional trailing comment, unquoting keys via the existing `unquote`. Skip blank and comment lines inside the block.

First, fix the custom_menus end-scan in `updateChatWheelYaml`: the current `while` loop treats column-0 comments and the trailing empty line as part of the block, so a comment after `custom_menus:` and the file-final newline are swallowed by the splice. Change the scan to stop after the last INDENTED NON-BLANK line, regardless of whether it is a comment. The rule must not be "non-comment": customMenusBlock() itself emits the indented placeholder `      # Add a command below` as the last line of a menu with empty items, and a rule that excludes indented comments would leave that placeholder outside the splice and duplicate it on every update. Under the non-blank rule, indented comments stay inside the owned range, while column-0 trailing comments and the file-final blank stay outside it. This is what makes the identity round trip and the starter.yml assertions in the behavior block true. (Comments and blank lines INSIDE the custom_menus block are still destroyed by the wholesale block regeneration; that is pre-existing behavior and out of scope. Identity claims about comments and blank lines therefore apply outside the custom_menus block.)

Then, after the custom_menus splice, apply each map in turn with a helper `applyOverrideBlock(lines, rootKey, desired)`. It re-locates the block on each call (the previous call may have shifted indices) and implements exactly the cases in the behavior block, using the same corrected end-scan rule. Lines inside the block that the entry regex does not match are outside the model's ownership: they are never rewritten and never deleted. The in-place rule for a changed entry: keep the original line, replacing only the trailing boolean token (regex on `true|false` before an optional comment at end of line), never re-serializing the key. Appends land immediately after the last parsed entry line, not after preserved comment or unparsed lines.

New-entry serialization uses a new `overrideKey(key)` helper. The regex is authoritative: plain when `/^[A-Za-z0-9(]([A-Za-z0-9 _.'()/-]*[A-Za-z0-9_.')-])?$/.test(key)` (starts with a letter, digit, or open paren; no leading or trailing space; `:` excluded so there is no colon-space hazard) AND the key is not a scalar a YAML 1.1 reader would resolve to a non-string: quote `y`, `n`, `yes`, `no`, `true`, `false`, `on`, `off`, `null` in any casing, `~`, and anything purely numeric. This is defensive: the loader's YAML version is unverified, and under YAML 1.1 `Yes`/`No` resolve to booleans, which config.gd's all-keys-strings validation would reject; quoting is harmless under YAML 1.2. It matters for real catalogue ids, since `Yes` and `No` are commands: NEW entries for them serialize as `"Yes": true`. (A pre-existing plain `Yes: true` line in user YAML is never rewritten; byte preservation wins, which is the correct trade-off.) Everything else falls to `JSON.stringify(key)`. Known limitation, fine to leave: JSON.stringify escapes `"` and backslash but `unquote` strips only the outer quote pair without unescaping, so an unknown user key containing those characters would not round-trip; no catalogue id contains either. Do NOT reuse the existing `quote()` for these keys: it excludes parentheses and apostrophes and would corrupt byte preservation (RESEARCH risk 1). Entries are written with two-space indent, `key: value`.

Add and export the two pure UI seams: `type OverrideState = 'inherit' | 'on' | 'off'`, `overrideStateFor(map: Record<string, boolean> | undefined, id: string): OverrideState`, and `applyOverride(model: ChatWheelModel, map: 'bindable' | 'pingWheel', id: string, state: OverrideState): ChatWheelModel`. applyOverride never mutates its input.

Extend `src/lib/chatWheelModel.test.ts` with a describe block using an inline fixture that carries, at minimum: a leading comment, a plain-safe unquoted `name:` (identity cannot hold for a quoted name; `quote()` rewrites it), an unknown root option, `override_bindable:` with one unquoted parenthesized key (`Good Game (Post Game) - All Chat: true`), one double-quoted key, one apostrophe key (`You're Welcome: false`), one unknown command id (`Totally Unknown Cmd: true`), one unparseable line (`Weird Key: TRUE`), an absent `override_ping_wheel_bindable`, a `custom_menus:` block in canonical serialized form, a trailing comment after the last block, and a file-final newline. This is the "small YAML fixture with known and unknown entries" REQ-cw-command-catalogue names: it must not import the catalogue module. Cover every behavior line above, including: identity round trip asserted with `toBe` on the whole string; single-toggle diff asserted by comparing line arrays (exactly one line differs); the absent-map-stays-absent case; the `Weird Key: TRUE` line surviving verbatim through a toggle of a neighbouring entry; the starter.yml shape (both maps inline `{}`, file-final newline intact) surviving an unrelated menu edit untouched; a `"Yes"`/`"No"` add serializing quoted; and a `parse(update(...))` equality check after each mutation.
  </action>
