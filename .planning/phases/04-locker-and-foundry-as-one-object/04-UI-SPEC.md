### Scope note — read before planning

**A load-bearing finding, verified against the working tree, not the docs.** Commit `f614bb7` ("feat(locker,foundry): close the parity gap between the two hero surfaces", already on `main`, an ancestor of `HEAD`) already implements all five lanes of `docs/locker-foundry-parity-plan.md` almost exactly as CONTEXT.md's D-04 through D-15 describe them. `ROADMAP.md` and `REQUIREMENTS.md` were written without this — they say lanes 2 to 5 are "no longer blocked" (i.e. pending), when the tree shows they already shipped. This is the same doc-drift pattern STATE.md already warns about ("doc status headers drift in both directions... work has been started three times on things that already shipped"). Concretely, verified in the current tree:

| Decision | Status in tree | Evidence |
|---|---|---|
| D-04/05/06 Foundry tray preview | **Delivered.** Debounced (700ms), builds only while `view3d` open, stacks staged edits over the enabled skin stack, releases on supersede/unmount/quit | `src/components/foundry/useTrayPreview.ts`, `electron/main/services/previewVpkRegistry.ts`, wired in `HeroWorkshop.tsx:117,153-173,277-314` |
| D-07/08 Locker pre-write disclosure, **sound only** | **Delivered** for `HeroSoundPicker`. `soundPickConsequence.ts` reuses `analyzeStagedEdits`; inline "takes over N / reverts M" copy renders beside the picker (`HeroSoundPicker.tsx:317-323`); `AssetSourcesPanel` docks into the Skins section as `HeroSkinOverlapPanel.tsx` | `src/components/locker/soundPickConsequence.ts`, `HeroSoundPicker.tsx` |
| D-07/08, **Effects tab (recolor/trippy)** | **Not delivered, and not a simple gap.** The parity commit's own message states why: "heroColors and trippyEffects discover the particle entries they patch at bake time, so there is no pre-write path set to disclose without a dry bake." | D-13/14 partial/D-15 Foundry grid state | **Mostly delivered.** Favorites are the shared `useHeroFavorites` store (canonical-name keyed, one shared `grimoire:hero-favorites` event); the change-count badge lifts `countFoundryChangesByHero` from the same rows `MyChanges` lists; the render fallback reuses the frame's four-step chain; `foundry.heroes.inDevelopment` is a real i18n key. **Gap: D-14's "distinguish zero from unavailable or still-loading" is not met** — the badge is simply absent both when `changeCount === 0` and while `!modsLoaded`, so a hero with genuinely zero changes and a hero whose mod list has not loaded yet render identically. See UI Considerations E6 | `src/components/foundry/FoundryHeroGrid.tsx:33-137,209-218` |
| D-01/02/03 composable replaceable stage | **Not delivered — this is the actual remaining UI-facing work of this phase.** Today both `LockerHero.tsx` and `HeroWorkshop.tsx` open the model in `FloatingModelPanel` (float / dock-left / dock-right, draggable, resizable) via a bespoke `3D` pill in `topRight`, layered **over** the 2D backdrop plate through the `after` slot. The backdrop itself never becomes the model: `HeroDetailFrame`'s `resolveHeroPlate()` only ever returns `'render'` or `'skinImage'`. Locker's toggle defaults to **closed** (`useModelPanelOpen` reads `localStorage`, false unless previously opened), so D-02's "the model is the primary stage when it can load" is not the default experience today. One seam already exists to build on: `src/lib/heroStage.ts`'s `HeroPlateKind` is already typed as `'render' \| 'skinImage' \| 'model'` and `heroPlateComposition()` already has a correct case for `'model'` (`{ className: 'absolute inset-0', usesRenderFallback: false }`) — nothing produces it yet | `src/components/common/HeroDetailFrame.tsx:79-107`, `src/lib/heroStage.ts:196-250`, `src/components/locker/useModelPanelOpen.ts` |

Every table row below therefore declares tokens for **new** elements only (the stage-mode control, the stage plate itself, the pop-out affordance, refined preview-state labels, and the grid loading badge). It does not restate colors/type/spacing for the already-shipped disclosure or image-sourcing UI, which an implementer should read at the file:line references above and leave alone.

**Visual hierarchy:**
- **Hero stage (`HeroDetailFrame`, both surfaces):** the plate — 2D render/skin image today, the model when this phase lands — remains the dominant visual element, full-bleed behind the rail and content pane. The new stage-mode control sits in `topRight`, visually secondary to the plate itself (small, translucent, backdrop-blurred chrome, matching the existing `3D` pill it replaces) so it reads as a control over the stage, not competing content.
- **Foundry tray-preview state chrome:** subordinate to the model itself. Status pills float at the top/bottom edge of the plate exactly as today's `Building preview` / `Preview build failed` chips do (`HeroWorkshop.tsx:296-312`) — small, translucent, never blocking the model.

Exactly 4 sizes, exactly 2 weights (400 regular / 600 semibold). No Display role — this phase adds no new page-level heading.

Notes specific to this phase:
- The stage-mode `SegmentedControl` options ("Model" / "Image") use the primitive's own built-in size (`text-xs font-medium`), which folds into the **Label** row above — do not override it with a custom size.
- The Locker auto-fallback banner (E4) and the refined tray-preview status pills (E5) use the **Compact** row (`text-[11px]`), matching the existing `Building preview`/`Preview build failed` pill copy size (`HeroWorkshop.tsx:298,306` are already `text-xs`; the *new* stale-label addition should match that existing `text-xs`, i.e. **Label**, not introduce an 11px variant for one pill and not the others it sits beside).
- The grid change-count loading indicator (E6) reuses the existing badge's exact type treatment (`text-[10px] font-semibold tabular-nums`, `FoundryHeroGrid.tsx:214`) — this is a pre-existing legacy 10px size on a control this phase does not otherwise restyle; copy it verbatim rather than inventing a fifth size.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `bg-bg-primary` `#0f0f0f` | App background, and the plate's own base fill when no hero art has resolved yet |
| Secondary (30%) | `bg-bg-secondary` `#1a1a1a` / `bg-bg-tertiary` `#242424` | Stage-mode control's unselected segment background (`SegmentedControl`'s existing `bg-bg-tertiary` unchanged), the Locker auto-fallback banner's body |
| Accent (10%) | `bg-accent` / `text-accent` / `border-accent` `#f97316` | Reserved for: the stage-mode control's **selected** segment (`SegmentedControl`'s existing `border-accent/70 bg-accent/15 text-text-primary`, unchanged), the pop-out button's pressed/active state, the "current" tray-preview status pill (new — the only one of the four preview states that gets accent, because it is the state that answers the question the preview exists to answer: "this is what forging now will look like"), and the focus ring (`focus-visible:ring-accent`) on every new interactive element |
| Destructive | `state-danger` `#f87171` | Reserved for the tray-preview **failed** state pill only (already shipped as `bg-red-500/20 text-red-200` at `HeroWorkshop.tsx:306` — extend that exact treatment, do not introduce a second red) |

Accent reserved for (explicit list, nothing else): the stage-mode control's selected segment, the pop-out button's active state, the "current" preview-state pill, and focus-visible rings. The **stale** and **loading/building** preview-state pills stay neutral (`bg-black/60 text-white/80`, matching the existing `Building preview` pill treatment) — accent must not spread to every state pill, only the one meaning "this is authoritative right now." The Locker auto-fallback banner uses `text-text-secondary` body copy with a `text-state-warning`-toned icon (matches the existing upscale/coverage warning pattern already shipped in `PortraitEditor.tsx:449-454,568-577`), never accent — it is informational, not a call to action.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Stage-mode control, Locker (`locker.hero.stageMode.model` / `.image`) | **"Model"** / **"Image"** — short segment labels, matching the terse style of the existing `3D` pill it replaces. Accessible label for the control (`locker.hero.stageModeLabel`): **"Hero stage view"** |
| Stage-mode control, Foundry (reuses the same keys — one shared presentation contract per D-03) | **"Model"** / **"Image"**, accessible label **"Hero stage view"**. Do not introduce Foundry-specific synonyms ("3D"/"2D", "Preview"/"Catalog") for the same two states — the whole point of D-03's shared contract is that both surfaces say the same thing for the same choice |
| Pop-out control (detach the model plate into the existing floating/dockable panel) | Icon-only `IconButton`, `label`/title = **"Open as floating panel"** (`locker.hero.popOutModel`). Reuses `FloatingModelPanel` unchanged once triggered — this is a presentation choice on the same model data, not a second viewer |
| Locker auto-fallback banner (Model attempted and failed, showing Image instead) | **"3D preview isn't available for this hero right now. Showing the image instead."** (`locker.hero.stageAutoFallback`) with an inline **"Retry"** action reusing the existing `locker.pose.retry` string verbatim — do not invent a second retry label |
| Locker auto-fallback banner, no game path configured | Reuses the existing `locker.pose.cannotPose`-adjacent taxonomy at the point it already exists; **do not** duplicate "no game path" copy here — link to Settings exactly as the existing pose failure state already does |
| Foundry tray-preview state pill: **stale** (new — showing the last valid build while a newer one is in flight) | **"Preview may be out of date"** (`foundry.workshop.previewStale`), rendered together with the existing "Building preview" pill rather than replacing it — two small pills, not one that tries to say both things |
| Foundry tray-preview state pill: **loading** (existing, unchanged) | Reuse `foundry.workshop.previewBuilding` = **"Building preview"** verbatim |
| Foundry tray-preview state pill: **failed** (existing, unchanged) | Reuse `foundry.workshop.previewFailed` = **"Preview build failed: {{error}}"** verbatim |
| Foundry tray-preview state pill: **current** (new — the build matches the tray's present state and nothing is in flight) | No pill at all. An unlabelled, unblemished model *is* the "current" state — adding a fourth pill for the default case would be visual noise for the common path. This is a deliberate absence, not an omission |
| Foundry grid change-count badge: **loading** (new — `!modsLoaded`, D-14's gap) | No numeral. A small neutral dot/pulse in the same top-left badge position (`foundry.heroes.changeCountLoading`, accessible text **"Change count is loading"**), replacing nothing visible today since the badge was previously simply absent pre-load. Must not render "0" during load: a loading "0" and a genuine zero are exactly the two states D-14 requires kept apart |
| Foundry grid change-count badge: **zero** (existing, unchanged) | No badge at all (absent, per the existing comment at `FoundryHeroGrid.tsx:209-210` — "Absent rather than '0': an empty badge would be noise on most of the roster"). This phase does not change that |
| Empty state (stage, no hero art of any kind resolves) | Unchanged — the existing hero-name-text fallback (`HeroDetailFrame.tsx:127-131`) already covers total failure; the new stage-mode control has nothing to add here since Model is simply unreachable and the control should reflect that (see UI Considerations E1) |
| Destructive confirmation | Not applicable — this phase ships no new destructive action. The stage-mode switch and pop-out are non-destructive, reversible view choices |

All copy above is written as **i18n key + English value**, per `docs/ui-conventions.md`'s "visible strings are i18n keys" rule and the standing project convention against hardcoded English or fallback-only strings. No em-dashes appear in any of the copy above (colon/period used instead), matching `CLAUDE.md`'s "no em-dashes anywhere" convention.

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5). Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text).

**Probe run:** 6 elements (the genuinely new/changed surface only — see Scope note for what is already delivered and out of scope), 33 applicable considerations — **21 covered, 11 backstop, 1 unresolved.**

### E1 — Stage-mode control (`SegmentedControl`, `topRight`, both surfaces)

| Category | Status | Resolution / Reason |
|----------|--------|---------------------|
| empty | ✅ covered | No hero art resolves at all (both render and model unavailable) → control still renders both segments (never hides a choice), but selecting Model falls straight through to the empty-plate text fallback (`HeroDetailFrame.tsx:127-131`), same as today |
| loading | 🧪 backstop | Whether the control shows a transient "checking availability" state before the first pose-info read resolves, or simply optimistically renders "Model" as selectable and lets the attempt fail inline (E4), is not settled by any decision. **verification: backstop** — the planner must pick one; do not silently assume |
| error | ✅ covered | Handled by E4 (Locker auto-fallback banner), not by the control itself. The control does not carry error state directly |
| populated | ✅ covered | Two-segment `SegmentedControl`, "Model" selected by default in Locker when pose data can plausibly resolve (D-02), "Image" selected by default in Foundry (D-02's Foundry half: "lazy, opt-in") |
| partial | ⚠ unresolved | A hero with a partially-resolvable stack (some enabled skins pose successfully, one does not) is the exact "stack failure vs single-skin failure" case `docs/locker-deep-dive.md`'s honesty-surfaces section describes as still in flight (`poseFailureStore.ts`, uncommitted per that doc as of 2026-07-30 — verify current status before planning). **Assumption for this contract:** the control shows "Model" as available whenever *any* valid pose export exists for the current stack, and per-skin attribution stays the existing card-badge mechanism's job, not this control's |
| overflow | ✅ covered | Two short fixed-width segment labels ("Model"/"Image") inside `topRight`'s existing flex row; no overflow surface introduced |
| zero-one-many | ✅ covered | Exactly two segments, always. Not a list — no zero/one/many question applies |
| long-text | 🧪 backstop | "Model"/"Image" in English are both short; no shipped locale's length is verified for this pair specifically. **verification: backstop** — check against the longest existing locale (matches Phase 3's precedent for the same open question on button labels) |

### E2 — Stage plate: the model as the backdrop (`HeroDetailFrame`, new `'model'` plate case)

| Category | Status | Resolution / Reason |
|----------|--------|---------------------|
| empty | ✅ covered | No pose data resolvable → the plate falls back to the existing `'render'`/`'skinImage'` chain unchanged, per D-02's "graceful fallback." The stage-mode control's Model segment stays selectable (so the user can retry), but the rendered plate is 2D until a build succeeds |
| loading | ✅ covered | While the model is resolving (first load, or a hero/skin switch), the plate shows the existing `HeroPoseViewer` loading treatment (`locker.pose.posing`/`posingWithMods`, already shipped) rather than a blank frame |
| error | ✅ covered | Reuses the existing pose-failure taxonomy (`locker.pose.cannotPose`/`skinFailed`/`exportFailed`, `HeroPoseViewer.tsx`) unchanged; this phase does not invent new error copy for the model itself, only the banner that explains *why the stage defaulted away from it* (E4) |
| populated | ✅ covered | Model fills the plate exactly as `heroPlateComposition()`'s existing `'model'` case already specifies (`absolute inset-0`, no fallback chain needed on this branch) — camera targets `heroSubjectX(heroName)` per `lib/heroStage.ts`'s documented (not yet consumed) contract, so the model lands where the calibrated 2D framing already puts the hero's face |
| partial | 🧪 backstop | Whether the veil's blur-over-a-live-canvas cost (measured inconclusive on capable hardware per `docs/locker-deep-dive.md`'s Axis 1, `tools/veil-blur-bench.js`) is acceptable on low-end GPUs is an open, human-measurement-gated question, not a design question. **verification: backstop** — this contract assumes the model is framed right of `clearZoneStart` (already a documented, derived token) so the veil samples the same static `bg-primary` it always has; if a low-end reading says otherwise, the fallback ladder in that doc (one blur layer, then a static snapshot, then keep the panel) is the design's own escape hatch and does not change this contract |
| overflow | ✅ covered | The plate fills its existing full-bleed container (`absolute inset-0` inside the frame's existing plate wrapper); no new overflow surface |
| zero-one-many | ✅ covered | One model per hero-detail view, matching the existing one-plate-at-a-time contract. Not a list |
| long-text | n/a | No text renders on the plate itself |
