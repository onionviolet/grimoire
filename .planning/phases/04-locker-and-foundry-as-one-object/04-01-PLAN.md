<planner_decisions>
Recorded so the executor does not re-litigate them. Each open item the source artifacts left unresolved is settled here with the alternative named beside it.

- **Stage-mode persistence uses a NEW key.** `grimoire.${surface}.heroStage.mode` holding `'model'` or `'image'`, in a new sibling hook. RESEARCH.md Open Question 2's recommendation, adopted: `useModelPanelOpen`'s existing `grimoire.${surface}.modelPanel.open` boolean genuinely means "is the floating panel open", and that meaning survives intact in this design (it becomes the pop-out state). Reinterpreting the same key as "is Model selected" would silently change what a stored value means for every user who ever opened the panel. Reversible: a migration that seeds the new key from the old one is additive if ever wanted.

- **Pop-out reuses `useModelPanelOpen` unchanged.** The model renders in exactly one place at a time: in the frame's plate when mode is `'model'` and the panel is closed, and inside `FloatingModelPanel` when the panel is open. Popping out therefore leaves the Model segment selected and drops the plate back to its image chain for as long as the panel is open, so closing the panel returns the model to the stage. This is why `FloatingModelPanel` needs no internal change.

- **E1's loading backstop is settled as optimistic Model-first (alternative recorded).** `get-hero-pose-info` reports `hasModel: false` for an uncached-but-exportable hero, indistinguishable from an unsupported one (`ipc/portraits.ts:128-137`), so it cannot gate the segment without wrongly denying Model to every hero without a cached export. The Locker therefore preselects Model and lets a definitive failure fall through to the E4 banner, which is the only reading that actually delivers D-02's "the model is the primary stage when it can load". **Reversible alternative if perceived Locker load time regresses:** flip `defaultHeroStageMode('locker')` to `'image'` and make Model an explicit pick, a one-line change in one function.

- **The auto-fallback flip is never persisted.** A definitive failure sets a per-mount displayed override, not the stored preference. Otherwise one unposable hero would demote the user's standing choice for the whole roster.

- **The auto-fallback banner is Locker-only, per UI-SPEC E4.** In Foundry the user opted into the preview explicitly, so a failed model keeps the plate on the model and shows `HeroPoseViewer`'s own failure state, which says why. Silently flipping Foundry back to Image would hide the reason the preview the user asked for is not there.

- **Per-hero camera framing is deferred, and this is a stated deviation from UI-SPEC E2's populated row.** That row asserts the camera targets `heroSubjectX(heroName)`. RESEARCH.md's assumption A1 shows why that is not a mechanical wire-up: `heroSubjectX` has zero call sites, `HERO_FACE_POSITION` is a percent of 2D art width hand-calibrated against 2D renders for 38 heroes, and no mapping from that space into 3D world space or an `OrbitControls` target exists. This phase ships `HeroPoseViewer`'s existing fixed camera (`position: [0, 0, 3.2], fov: 40`) for every hero and leaves `heroSubjectX` unconsumed. Per-hero calibration is recorded below as an explicitly deferred item, not as an omission.

- **UI-SPEC E1's `partial` row is an unresolved assumption carried forward, not dropped.** The contract's own assumption stands: the Model segment is treated as available whenever any valid pose export exists for the current stack, and per-skin attribution stays `poseFailureStore.ts`'s job through the existing card badges. RESEARCH.md Pitfall 3 confirms that mechanism is committed and shipped; do NOT write a task that rebuilds it. What is genuinely still missing is only a typed `reason` field on `HeroPoseInfo`, which is out of this phase's scope, so the banner's copy stays hero-level and generic.

- **UI-SPEC's probe header count is stale.** It reads "33 applicable considerations, 21 covered, 11 backstop, 1 unresolved"; its own tables hold 41 applicable rows (34 covered, 6 backstop, 1 unresolved). The tables are the content and were lifted from; the header is a bad arithmetic line. Recorded so a later reader does not mistake the difference for a drop.

- **Below the `lg` breakpoint nothing changes.** The frame's plate wrapper is already `hidden lg:block` and the layout stacks into a column, so Model mode has no plate to fill on a narrow window. The stage-mode control still renders (E1 never hides a choice) and the pop-out remains the way to see the model there. This is existing behaviour, preserved, not a new limitation.

- **`useTrayPreview.ts` is read-only in this plan.** `building && previewId !== null` is already true for exactly the window D-06 describes, because `replace(null)` is never called on the rebuild path (`useTrayPreview.ts:59-95`). Adding a `stale` field to the hook would state the same fact twice.
